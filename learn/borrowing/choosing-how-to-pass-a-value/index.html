Choosing how to pass a value

You now have four ways to hand a value to a function. Choosing well is most of what "idiomatic Rust" means for function signatures:

The function... Parameter Example
only reads the value &T fn total(items: &Vec<u32>) -> u32
changes the value in place &mut T fn restock(items: &mut Vec<u32>, n: u32)
keeps the value, or uses it up T (move) fn archive(report: String)
gets a small Copy value T (copy) fn is_adult(age: u32) -> bool
creates new data returns an owned T fn make_label(...) -> String

Here's a bank account that uses all of them:

fn print_statement(owner: &String, history: &Vec<i64>) {
    let mut balance = 0;
    for amount in history {
        balance += amount;
    }
    println!("{}: {} transactions, balance {}", owner, history.len(), balance);
}

fn deposit(history: &mut Vec<i64>, amount: i64) {
    history.push(amount);
}

fn close_account(owner: String, history: Vec<i64>) -> String {
    format!("closed {}'s account after {} transactions", owner, history.len())
}

fn main() {
    let owner = String::from("Ferris");
    let mut history = vec![100];
    deposit(&mut history, 50);
    deposit(&mut history, -30);
    print_statement(&owner, &history);
    let receipt = close_account(owner, history);
    println!("{}", receipt);
}

Ferris: 3 transactions, balance 120
closed Ferris's account after 3 transactions
  • print_statement only reads, so it borrows: main keeps both values.
  • deposit changes the history, so it borrows mutably.
  • close_account takes ownership on purpose: after closing, the account must not be used again, and now the compiler guarantees it. Any later use of owner or history is a compile error. Moves aren't only about memory; they also let a type say "this is finished".

Workplace notes

  • In a typical Rust codebase, most parameters are &T. &mut T appears where a function's job is to change something, and owned parameters where the function stores or consumes the value.
  • Don't pass small Copy values by reference: fn is_adult(age: &u32) just makes callers write &. (Clippy's pedantic lints flag it as trivially_copy_pass_by_ref.)
  • Clippy warns about &String and &Vec<T> parameters (the ptr_arg lint). The next module, slices, shows why &str and &[T] are better parameter types. Everything you've learned here carries over unchanged.
  • The borrowing rules cost nothing at run time: references are plain pointers, and all checking happens at compile time.

Common mistakes

  • Taking ownership "to be safe", then cloning at every call site. If you only read, borrow.
  • Taking &mut when & would do. It blocks other readers for no reason.
  • Returning references to new data (step 6). Return owned values.
