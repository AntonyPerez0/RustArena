Putting it together: Config, run() and clap

Every well-built Rust CLI ends up with the same shape:

fn main() -> ExitCode {
    let args: Vec<String> = std::env::args().skip(1).collect();
    let command = match parse_args(&args) {      // 1. arguments -> a typed Config/Command
        Ok(c) => c,
        Err(msg) => {
            eprintln!("{msg}\n{USAGE}");
            return ExitCode::from(2);            //    usage errors: exit 2
        }
    };
    match run(command) {                         // 2. do the work, returning Result
        Ok(()) => ExitCode::SUCCESS,
        Err(e) => {
            eprintln!("error: {e}");             // 3. report on stderr
            ExitCode::FAILURE                    //    failures: exit 1
        }
    }
}
  • Parsing turns strings into a typed value (a Config struct, or an enum with one variant per subcommand). After this point, nothing looks at raw arguments.
  • run does the work and returns Result, so it can use ? everywhere (with anyhow and context from the last module, in a real project).
  • main is the only place that knows about exit codes and the usage text.
  • The decisions inside run live in small functions over &str and plain values, which unit tests can call directly.

clap: what teams use for real

Hand-written parsing is fine for small tools. For anything bigger, teams use the clap crate. You describe the arguments as a struct, and #[derive(Parser)] generates the parser, --help, --version, clear error messages (including suggestions for misspelled flags), and exit code 2 for usage errors. clap isn't available on this site, so here's what it looks like (not compiled):

[dependencies]
clap = { version = "4", features = ["derive"] }

use clap::{Parser, Subcommand};

/// A tiny todo list
#[derive(Parser)]
#[command(version)]
struct Cli {
    /// File that stores the tasks
    #[arg(short, long, default_value = "todo.txt")]
    file: String,

    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    /// Show all tasks
    List,
    /// Add a task
    Add { text: Vec<String> },
    /// Mark task N as done
    Done { n: usize },
}

fn main() {
    let cli = Cli::parse(); // on bad arguments: prints the error and exits with 2
    match cli.command {
        Command::List => { /* ... */ }
        Command::Add { text } => { /* ... */ }
        Command::Done { n } => { /* ... */ }
    }
}

The /// doc comments become the help text:

$ todo --help
A tiny todo list

Usage: todo [OPTIONS] <COMMAND>

Commands:
  list  Show all tasks
  add   Add a task
  done  Mark task N as done
  help  Print this message or the help of the given subcommand(s)

Options:
  -f, --file <FILE>  File that stores the tasks [default: todo.txt]
  -h, --help         Print help
  -V, --version      Print version

Notice it's the same design as this module's: a typed struct, an enum of subcommands, match in main. The Pro Track builds a complete CLI with clap, anyhow and integration tests; everything you practiced here carries over directly.

Common mistakes

  • Business logic in main. It can't be unit-tested and mixes concerns. Move it to functions.
  • process::exit deep in helper functions: the code becomes impossible to test and skips cleanup. Return errors; let main decide.
  • A usage message that doesn't say what's wrong. Print the specific problem first (unknown command "lst"), then the usage.

Your task

Build todo, a todo list stored in todo.txt, one task per line written as [ ] text or [x] text (done). Commands:

  • list: print each task as 1. [ ] buy milk; if there are none (or the file doesn't exist yet), print no tasks.
  • add <words>...: append [ ] <words joined by spaces> to the file and print added 3: buy milk (3 is the new task's number).
  • done <n>: mark task n as done, write the file back, and print done 2: feed the crab. If there's no task n (that includes 0), print error: no task 7 to stderr and exit 1.
  • No command, an unknown command, add without words or done without a valid number: print usage: todo list | add <text> | done <n> to stderr and exit 2.
