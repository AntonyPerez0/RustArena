Rc<T>: shared ownership

Ownership says every value has exactly one owner. Most of the time that's what you want. But sometimes several parts of a program need to own the same value, and there's no obvious one that lives longest: a song that's on several playlists, a config shared by several services, a node in a graph with several incoming edges.

Rc<T> (reference counted) allows that. Rc::new(value) puts the value on the heap together with a counter. Rc::clone(&rc) makes another pointer to the same value and adds 1 to the strong count. Dropping an Rc subtracts 1. When the count reaches 0, the value is dropped.

use std::rc::Rc;

struct Song {
    title: String,
}

fn main() {
    let song = Rc::new(Song { title: String::from("Crab Rave") });
    println!("count after new: {}", Rc::strong_count(&song));

    let workout = vec![Rc::clone(&song)];
    {
        let road_trip = vec![Rc::clone(&song)];
        println!("count with two playlists: {}", Rc::strong_count(&song));
        println!("road trip plays {}", road_trip[0].title);
    }
    println!("count after the road trip: {}", Rc::strong_count(&song));
    println!("workout plays {}", workout[0].title);
}

count after new: 1
count with two playlists: 3
road trip plays Crab Rave
count after the road trip: 2
workout plays Crab Rave
  • Rc::clone(&song) doesn't copy the Song. It copies a pointer and bumps the counter, which is very cheap. song.clone() does the same thing, but Rust code conventionally writes Rc::clone(&song) so readers can see at a glance that it's a cheap pointer copy and not a deep copy.
  • road_trip[0].title reaches through the Rc with Deref, like a Box.
  • When the inner block ends, road_trip is dropped, its Rc with it, and the count goes from 3 to 2. The song itself stays alive until the last Rc is gone.

Rc is read-only and single-threaded

An Rc<T> only hands out shared references (&T). With several owners, letting any one of them mutate would break the "one writer" rule, so this doesn't compile:

use std::rc::Rc;

fn main() {
    let scores = Rc::new(vec![1, 2]);
    scores.push(3);
    println!("{scores:?}");
}

error[E0596]: cannot borrow data in an `Rc` as mutable

To change shared data, combine Rc with RefCell (next two steps). And Rc updates its counter without any thread synchronization, so the compiler won't let you send it to another thread. Its thread-safe twin is Arc<T> (atomically reference counted), coming in the concurrency modules.

Common mistakes

  • Expecting Rc::clone to copy the data. All clones point at the same value.
  • Reaching for Rc to quiet the borrow checker. If one owner clearly outlives the others, plain references (&T) are simpler and free. Use Rc when ownership really is shared.
  • Trying to mutate through it: error[E0596] as above.

Challenge 3

A tournament player can be on several teams. Write:

  • fn share(player: Player, teams: &mut [Team]) -> Rc<Player>: wraps the player in one Rc, adds a clone of it to every team's members, and returns the Rc (so the caller keeps one handle too).
