Ordering: PartialOrd and Ord for sorting

v.sort() needs the items to implement Ord, a total order: for any two values, one is less, greater or equal. Deriving Ord (previous module) compares the fields in the order they're written. When you need a different order, implement it yourself.

A leaderboard: higher scores first, and players with the same score alphabetically.

use std::cmp::Ordering;

#[derive(Debug, PartialEq, Eq)]
struct Player {
    name: String,
    score: u32,
}

impl Ord for Player {
    fn cmp(&self, other: &Self) -> Ordering {
        other.score.cmp(&self.score).then(self.name.cmp(&other.name))
    }
}

impl PartialOrd for Player {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

fn main() {
    let mut board = vec![
        Player { name: String::from("cy"), score: 80 },
        Player { name: String::from("bo"), score: 95 },
        Player { name: String::from("al"), score: 80 },
    ];
    board.sort();
    for p in &board {
        println!("{} {}", p.score, p.name);
    }
}

95 bo
80 al
80 cy

Piece by piece:

  • std::cmp::Ordering is an enum with three values: Less, Equal, Greater. a.cmp(&b) on numbers and strings returns one.
  • other.score.cmp(&self.score) compares in reverse (other first), which puts higher scores first. You could also write self.score.cmp(&other.score).reverse().
  • .then(...) breaks ties: it's used only when the first comparison says Equal.
  • PartialOrd is required too (it powers < and >). When you have Ord, implement it as Some(self.cmp(other)) so the two always agree.
  • Ord also needs Eq and PartialEq, here derived.

Keep them consistent

==, cmp and < must agree: if cmp says Equal, == must say true. Here PartialEq compares both fields and cmp uses both fields, so they agree. If cmp ignored the name, two players with the same score would be "equal" for sorting but not for ==, and collections like BTreeSet would treat them as duplicates. Compare the same fields in all of them.

Implement Ord, or use sort_by?

Implement Ord when the type has one natural order that everyone expects: versions, priorities, dates. For a one-off order in one place ("sort these players by name for this report"), use sort_by or sort_by_key from the vectors module and leave the type alone:

board.sort_by(|a, b| a.name.cmp(&b.name));

Floats aren't Ord

f64 has NaN, which isn't less, equal or greater than anything, so floats only implement PartialOrd:

fn main() {
    let mut times: Vec<f64> = vec![9.58, 9.63, 9.69];
    times.sort();
    println!("{:?}", times);
}

error[E0277]: the trait bound `f64: Ord` is not satisfied

Use times.sort_by(|a, b| a.total_cmp(b));. total_cmp gives every float (even NaN) a fixed place in the order.

Common mistakes

  • Ord without its companions. impl Ord needs PartialOrd, Eq and PartialEq too; leaving out PartialOrd gives error[E0277]: can't compare `Player` with `Player` . Derive PartialEq, Eq and write partial_cmp as Some(self.cmp(other)).
  • Deriving PartialOrd but writing Ord by hand (or the other way round). Then < uses the field order and sort() uses your logic, and they disagree. Clippy flags it (derive_ord_xor_partial_ord). Write both by hand, with partial_cmp calling cmp.
  • Reversing the wrong way. self.score.cmp(&other.score) puts the lowest score first. For "highest first", swap self and other, or add .reverse().
