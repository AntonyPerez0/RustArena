JSON in, JSON out

JSON APIs send JSON in request bodies and get JSON back. With serde (from the serde module), a handler is three moves: deserialize the body into a request type, check it, serialize the result.

use serde::{Deserialize, Serialize};
use serde_json::json;

#[derive(Deserialize)]
struct CreateUser {
    name: String,
    email: String,
}

#[derive(Serialize)]
struct User {
    id: u32,
    name: String,
    email: String,
}

struct Response {
    status: u16,
    body: String,
}

fn json_response<T: Serialize>(status: u16, value: &T) -> Response {
    Response { status, body: serde_json::to_string(value).expect("response types always serialize") }
}

fn create_user(body: &str, next_id: u32) -> Response {
    let input: CreateUser = match serde_json::from_str(body) {
        Ok(input) => input,
        Err(e) => return json_response(400, &json!({ "error": format!("invalid JSON: {e}") })),
    };
    if !input.email.contains('@') {
        return json_response(422, &json!({ "error": "email must contain @" }));
    }
    let user = User { id: next_id, name: input.name, email: input.email };
    json_response(201, &user)
}

fn main() {
    for body in [r#"{"name": "Ana", "email": "ana@arena.dev"}"#, r#"{"name": "Bo", "email": "bo"}"#, r#"{"name": "Cy"}"#] {
        let r = create_user(body, 7);
        println!("{} {}", r.status, r.body);
    }
}

201 {"id":7,"name":"Ana","email":"ana@arena.dev"}
422 {"error":"email must contain @"}
400 {"error":"invalid JSON: missing field `email` at line 1 column 14"}

Piece by piece:

  • CreateUser and User are separate types on purpose. These DTOs (data transfer objects) describe exactly what crosses the wire: the client doesn't send an id (the server assigns it), and a response type is where you leave out fields that must never leave the server (a password hash, internal flags). Changing your internal model then doesn't silently change your API.
  • json_response is a generic helper: any T: Serialize becomes a response with a status. Errors use the same shape every time, {"error": "..."}, so clients can handle them in one place.
  • 400 vs 422: 400 when the body isn't valid JSON or has the wrong shape; 422 when it parses fine but breaks a business rule. (Some APIs use 400 for both; pick one convention and stick to it.)
  • Real responses also carry a Content-Type: application/json header; frameworks set it for you when you return JSON.

Common mistakes

  • Deserializing straight into your database model: a client could then send "id": 1 or "is_admin": true and have it accepted. Request DTOs list only what clients may set.
  • unwrap() on the request body. One malformed request would crash the handler (in a server, the panic usually just drops that connection, or becomes a 500 if you add a catch-panic middleware; either way the client gets no useful answer and your logs fill with panics). Bad input is a 400, not a crash.
  • Building JSON by hand with format!("{{\"name\":\"{}\"}}", name): a name containing " produces broken JSON (and an injection risk). Let serde escape it.

Your task

Write create_ticket. The body looks like {"title": "Printer on fire", "priority": "high"}; priority is optional and defaults to normal. Respond with:

  • 400 and {"error":"invalid request body"} if the body doesn't parse (including an unknown priority),
  • 422 and {"error":"title must not be empty"} if the title is empty after trimming,
  • otherwise 201 with the ticket: {"id":<next_id>,"title":"<trimmed title>","priority":"high","status":"open"}.
