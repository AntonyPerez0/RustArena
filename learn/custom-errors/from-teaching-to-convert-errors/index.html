From: teaching ? to convert errors

Box<dyn Error> accepts every error, but it forgets which one it was. For an error type that callers can match on, you want an enum that wraps the lower-level errors:

enum ConfigError {
    MissingEquals(String),       // the bad line
    BadNumber(ParseIntError),    // the parse error, kept inside
}

Now try to use ? on a parse() in a function returning Result<_, ConfigError>:

use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    BadNumber(ParseIntError),
}

fn parse_value(text: &str) -> Result<u32, ConfigError> {
    let n = text.trim().parse::<u32>()?;
    Ok(n)
}

fn main() {
    println!("{:?}", parse_value("12"));
}

error[E0277]: `?` couldn't convert the error to `ConfigError`
  |                         --------------^ the trait `From<ParseIntError>` is not implemented for `ConfigError`
  = note: the question mark operation (`?`) implicitly performs a conversion on the error value using the `From` trait

The note tells the whole story. Here's what ? really does on an error:

match expression {
    Ok(value) => value,
    Err(e) => return Err(From::from(e)),   // convert, then return
}

From is the standard trait for "make one type out of another". When you call ?, Rust looks for a way to make the function's error type from the error it got. Box<dyn Error> has From for every error type, and also for &str and String messages: that's why those conversions worked in the last step. For your own enum, you write the conversion:

use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    MissingEquals(String),
    BadNumber(ParseIntError),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ConfigError::MissingEquals(line) => write!(f, "missing '=' in {line:?}"),
            ConfigError::BadNumber(e) => write!(f, "bad number: {e}"),
        }
    }
}

impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::BadNumber(e)
    }
}

fn parse_line(line: &str) -> Result<(String, u32), ConfigError> {
    let (key, value) = line
        .split_once('=')
        .ok_or_else(|| ConfigError::MissingEquals(line.to_string()))?;
    let value: u32 = value.trim().parse()?;
    Ok((key.trim().to_string(), value))
}

fn main() {
    for line in ["timeout = 30", "retries = lots", "verbose"] {
        match parse_line(line) {
            Ok((key, value)) => println!("{key} = {value}"),
            Err(e) => println!("error: {e}"),
        }
    }
}

timeout = 30
error: bad number: invalid digit found in string
error: missing '=' in "verbose"
  • impl From<ParseIntError> for ConfigError reads "here's how to make a ConfigError from a ParseIntError". The one method, from, takes the error and returns Self (the type being implemented, ConfigError).
  • In parse_line, value.trim().parse()? now compiles: on error, ? calls ConfigError::from(e), which wraps it in BadNumber.
  • The original ParseIntError is kept inside, not turned into text, so nothing is lost.
  • A From implementation also gives you .into() for free: let e: ConfigError = parse_error.into();.

The quick alternative: map_err with a variant

For a one-off conversion, map_err works too, and a tuple variant can be passed as if it were a function:

let value: u32 = value.trim().parse().map_err(ConfigError::BadNumber)?;

Use From when the same conversion happens in many places (it's then automatic everywhere), and map_err when it's a single spot or when the same source error should become different variants in different places.

Common mistakes

  • Two variants wrapping the same error type. You can only write one From<ParseIntError> for ConfigError, so ? can't know whether a parse error is a bad port or a bad timeout. Use map_err to pick the variant at each call site, or keep the context in the variant: BadNumber { key: String, source: ParseIntError }.
  • Writing From in the wrong direction. impl From<ConfigError> for ParseIntError would convert the other way. The type after for is the one being created.
  • Converting the error to a String too early. BadNumber(String) with e.to_string() loses the original error and its type. Keep the error value; the next step shows why that matters.
