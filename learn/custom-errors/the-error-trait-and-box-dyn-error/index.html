The Error trait and Box<dyn Error>

The standard library has a trait that marks a type as "an error": std::error::Error. Implementing it is one line, because all of its methods have default versions:

impl std::error::Error for WithdrawError {}

There's one requirement: the type must already implement Debug and Display. That's the contract of an error in Rust: it can be shown to developers ({:?}) and to users ({}).

Why bother? Because code that works with any error, from the standard library, from crates like anyhow, and from your own programs, works through this trait. ParseIntError, ParseFloatError and std::io::Error all implement it.

Box: "some error"

A function that can fail in several different ways, with different error types, needs one return type that fits them all. The standard answer is Box<dyn Error>:

  • dyn Error means "a value of some type that implements Error; which one is decided at run time". Module 25 covers these trait objects.
  • Box<...> puts that value on the heap, because different error types have different sizes. Module 29 covers Box.

Together: Result<T, Box<dyn Error>> means "a T, or any kind of error". And ? converts any error type that implements Error into a Box<dyn Error> for you. Even a plain &str or String message converts.

use std::error::Error;
use std::fmt;

#[derive(Debug)]
struct EmptyLine;

impl fmt::Display for EmptyLine {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "line is empty")
    }
}

impl Error for EmptyLine {}

fn parse_order(line: &str) -> Result<(String, u32), Box<dyn Error>> {
    let line = line.trim();
    if line.is_empty() {
        return Err(Box::new(EmptyLine));
    }
    let (item, qty) = line.split_once(',').ok_or("expected ITEM,QTY")?;
    let qty: u32 = qty.trim().parse()?;
    Ok((item.to_string(), qty))
}

fn main() {
    for line in ["apples, 3", "pears,many", "", "plums"] {
        match parse_order(line) {
            Ok((item, qty)) => println!("{qty} x {item}"),
            Err(e) => println!("error: {e}"),
        }
    }
}

Three different error types flow through one return type:

  • EmptyLine, your own (a unit struct: an error with no data), boxed by hand with Box::new.
  • A &str message: ok_or("expected ITEM,QTY") makes a Result<_, &str>, and ? boxes the message.
  • ParseIntError from parse, boxed by ?.

The caller prints each with {}; the box forwards to the real error's Display.

main returning Box

This fixes the problem from the last module: read_line fails with io::Error, parse with ParseIntError, and a main returning Result<(), Box<dyn Error>> accepts both:

use std::error::Error;
use std::io::BufRead;

fn main() -> Result<(), Box<dyn Error>> {
    let mut total: i64 = 0;
    for line in std::io::stdin().lock().lines() {
        let line = line?;
        let amount: i64 = line.trim().parse()?;
        total += amount;
    }
    println!("total: {total}");
    Ok(())
}

fn main() -> Result<(), Box<dyn Error>> is the standard signature for small programs, scripts and examples.

The trade-off

A Box<dyn Error> has forgotten its concrete type. The caller can print it, but can't match on your variants (getting the type back needs downcasting, module 25). So:

  • Applications (a main, a script, a command-line tool) mostly just report errors: Box<dyn Error> (or anyhow, step 7) is great.
  • Libraries and modules whose callers need to react to specific failures should return a concrete error enum.

Common mistakes

  • Implementing Error without Display:
#[derive(Debug)]
struct EmptyLine;

impl std::error::Error for EmptyLine {}

fn main() {}

error[E0277]: `EmptyLine` doesn't implement `std::fmt::Display`
  • Returning your error unboxed. return Err(EmptyLine); in a function returning Box<dyn Error> is a mismatched types error: expected `Box<dyn Error>`, found `EmptyLine` . Write Err(Box::new(EmptyLine)) or Err(EmptyLine.into()). Only ? boxes automatically.
  • Comparing Box<dyn Error> results with assert_eq!. They don't implement PartialEq. In tests, compare the message: assert_eq!(err.to_string(), "line is empty").
