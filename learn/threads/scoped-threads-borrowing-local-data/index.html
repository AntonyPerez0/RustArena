Scoped threads: borrowing local data

Copying chunks with to_vec() just to satisfy 'static is wasteful. Borrowing would be safe if you could promise that every thread ends before the borrowed data is dropped. thread::scope turns that promise into something the compiler can check:

use std::thread;

fn main() {
    let readings: Vec<u32> = (1..=12).collect();
    let total = thread::scope(|s| {
        let mut handles = Vec::new();
        for chunk in readings.chunks(4) {
            handles.push(s.spawn(|| chunk.iter().sum::<u32>()));
        }
        handles.into_iter().map(|h| h.join().unwrap()).sum::<u32>()
    });
    println!("total: {total}");
    println!("main still owns all {} readings", readings.len());
}

total: 78
main still owns all 12 readings

How it works:

  • thread::scope(|s| { ... }) calls your closure with a scope s. Threads started with s.spawn(...) are scoped threads.
  • Before thread::scope returns, it joins every thread spawned in the scope that you didn't join yourself. So no scoped thread can outlive the scope, and the compiler lets them borrow anything that lives longer than the scope, like readings.
  • s.spawn returns a ScopedJoinHandle, which you join exactly like a normal handle.
  • Whatever the closure returns, thread::scope returns: here the total.

No to_vec(), no move, no copies: each thread reads its chunk straight out of readings.

Mutable borrows work too

The borrowing rules still apply across threads: one &mut at a time per piece of data. chunks_mut cuts a slice into pieces that don't overlap, so each thread can get its own &mut piece:

use std::thread;

fn main() {
    let mut prices = vec![100, 250, 80, 40, 60, 500];
    thread::scope(|s| {
        for chunk in prices.chunks_mut(2) {
            s.spawn(|| {
                for p in chunk {
                    *p = *p * 90 / 100;
                }
            });
        }
    });
    println!("{prices:?}");
}

[90, 225, 72, 36, 54, 450]

This time we don't keep the handles: the scope joins all the threads for us before println! runs.

Lazy iterators and joining

A tempting one-liner is data.chunks(n).map(|c| s.spawn(...)).map(|h| h.join().unwrap()).sum(). Iterators are lazy (module 27): each item goes through both maps before the next chunk is touched, so every thread is joined right after it starts, and they run one at a time. Collect the handles into a Vec first, then join.

scope or spawn?

  • thread::scope: the threads do a piece of work inside one function and are done before it returns. Most "split this job over the cores" code looks like this.
  • thread::spawn with move: the thread must outlive the function that started it, like a background worker that runs for the whole program.

Common mistakes

  • chunks(0) panics. A chunk size from data.len() / workers is 0 when there are fewer items than workers. div_ceil divides and rounds up (10_usize.div_ceil(4) is 3), and .max(1) keeps the size at least 1.
  • Loop variables still need move. for i in 0..4 { s.spawn(|| i * 2); } borrows i, which dies at the end of each turn of the loop: E0373. Write s.spawn(move || i * 2). If the closure also uses a Vec, move would move the whole Vec into the first thread; make a reference first (let data = &data;) and move that: copying a reference is free.
  • Two threads writing the same variable: E0499, explained in the next step.
