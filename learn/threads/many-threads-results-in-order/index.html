Many threads, results in order

Real work gets split over several threads. The pattern every team uses:

  1. Spawn the threads in a loop and keep every JoinHandle in a Vec.
  2. When all of them are running, join them in the order you spawned them.

Each thread finishes whenever it finishes, but because you collect results in spawn order, the output is the same on every run. This example makes it visible with thread::sleep, which pauses the current thread for a Duration (from std::time). The workers that sleep longer finish later:

use std::thread;
use std::time::Duration;

fn main() {
    let jobs = vec![("resize", 30), ("compress", 10), ("upload", 20)];
    let mut handles = Vec::new();
    for (name, ms) in jobs {
        handles.push(thread::spawn(move || {
            thread::sleep(Duration::from_millis(ms));
            format!("{name} done after {ms} ms")
        }));
    }
    for handle in handles {
        println!("{}", handle.join().unwrap());
    }
}

resize done after 30 ms
compress done after 10 ms
upload done after 20 ms

compress finished first, but main waited for resize first, so the results come out in spawn order. Joining a thread that already finished returns at once. The whole program takes about 30 ms, not 60, because the three sleeps overlap.

move is needed here: each closure uses name and ms, which are local to one turn of the loop.

Splitting data into chunks

To process a big list, give each thread one piece. chunks(n) (module 27) cuts a slice into pieces of n items (the last one may be shorter). A spawned thread must own its data, so each borrowed chunk is copied into its own Vec with to_vec():

use std::thread;

fn main() {
    let readings: Vec<u32> = (1..=12).collect();
    let mut handles = Vec::new();
    for chunk in readings.chunks(4) {
        let part = chunk.to_vec();
        handles.push(thread::spawn(move || part.iter().sum::<u32>()));
    }
    let sums: Vec<u32> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("partial sums: {sums:?}");
    println!("total: {}", sums.iter().sum::<u32>());
}

partial sums: [10, 26, 42]
total: 78

Copying every chunk costs time and memory. The next step removes the copy.

How many threads?

Threads aren't free: each one gets its own stack (2 MiB by default for spawned threads) and takes some microseconds to start. For CPU-heavy work, about one thread per core is right; thread::available_parallelism() tells you how many cores the machine offers. Spawning a thread per item for a million items would spend more time managing threads than working.

Common mistakes

  • Joining inside the spawn loop: handles.push(thread::spawn(f).join().unwrap()) waits for each thread before starting the next, so they run one at a time.
  • Looping over &handles: join takes the handle by value (it consumes it), so for h in &handles { h.join(); } fails with error[E0507]: cannot move out of `*h` which is behind a shared reference. Loop over handles itself.
  • Expecting the fastest worker's result first: results come in the order you join, which is the point.
