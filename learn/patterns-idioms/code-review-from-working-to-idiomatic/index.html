Code review: from working to idiomatic

At work, most of the Rust you write gets reviewed before it's merged, and much of what reviewers flag is the same short list. Many of those comments are automated by clippy (cargo clippy), and the rest you now know from this course. Here are the classics, with the clippy lint name where there is one:

Teams switch on stricter lints per project, in Cargo.toml:

[lints.clippy]
unwrap_used = "warn"
pedantic = { level = "warn", priority = -1 }

and CI runs cargo clippy -- -D warnings so warnings fail the build.

A small refactor

Both versions below print the same thing. The first is what a newcomer from another language writes; the second is what a reviewer hopes to see.

fn average_score(scores: &Vec<u32>) -> f64 {
    if scores.len() == 0 {
        return 0.0;
    }
    let mut sum = 0;
    for i in 0..scores.len() {
        sum = sum + scores[i];
    }
    return sum as f64 / scores.len() as f64;
}

fn main() {
    println!("{:.2}", average_score(&vec![70, 85, 90]));
    println!("{:.2}", average_score(&vec![]));
}

81.67
0.00

fn average_score(scores: &[u32]) -> f64 {
    if scores.is_empty() {
        return 0.0;
    }
    let sum: u32 = scores.iter().sum();
    sum as f64 / scores.len() as f64
}

fn main() {
    println!("{:.2}", average_score(&[70, 85, 90]));
    println!("{:.2}", average_score(&[]));
}

81.67
0.00

(The early return for the empty case is fine: needless_return only flags a return on the last line.)

How to refactor safely

  1. Pin the behavior first: make sure tests cover what the code does today, including edge cases (empty input, ties, bad input). On this site, the hidden tests play that role.
  2. One change at a time, re-running the tests after each: types first (&Vec to &[T], strings to enums), then loops to iterators, then error handling.
  3. Watch for behavior changes hiding in "cleanups": max_by_key returns the last maximum on ties while a hand-written > loop keeps the first; replacing unwrap with unwrap_or_default turns a crash into silently wrong data. A refactor that changes behavior isn't a refactor.
  4. Turning panics into errors does change the signature (-> Result<..>). That's an improvement, but it's an API change your callers must know about.
