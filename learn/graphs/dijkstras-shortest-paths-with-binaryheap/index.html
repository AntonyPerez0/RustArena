Dijkstra's shortest paths with BinaryHeap

When edges have weights (kilometers, minutes, milliseconds of latency, euros), the path with the fewest edges isn't necessarily the cheapest. Dijkstra's algorithm finds the cheapest path from one start node to every other node, as long as no weight is negative.

The idea: repeatedly take the not-yet-settled node with the smallest known distance. Its distance is final, because any other way to reach it would go through a node that is already at least as far away. Then try to improve its neighbors' distances through it (relaxing the edges).

"Take the node with the smallest distance" is exactly what a min-heap is for: a BinaryHeap<Reverse<(u64, usize)>> of (distance, node) pairs. Rust's heap can't lower an item's priority in place, so when a distance improves you simply push a new pair; when an outdated pair pops later (its distance is bigger than the best known one), you skip it. This is called lazy deletion.

use std::cmp::Reverse;
use std::collections::BinaryHeap;

fn dijkstra(adj: &[Vec<(usize, u64)>], start: usize) -> Vec<u64> {
    let mut dist = vec![u64::MAX; adj.len()]; // u64::MAX = not reached
    let mut heap = BinaryHeap::new();
    dist[start] = 0;
    heap.push(Reverse((0, start)));
    while let Some(Reverse((d, u))) = heap.pop() {
        if d > dist[u] {
            continue; // stale entry: a shorter way to u was found later
        }
        for &(v, weight) in &adj[u] {
            let through_u = d + weight;
            if through_u < dist[v] {
                dist[v] = through_u;
                heap.push(Reverse((through_u, v)));
            }
        }
    }
    dist
}

fn main() {
    // warehouse 0 and four shops; (to, minutes) one-way roads
    let adj = vec![
        vec![(1, 4), (2, 1)],
        vec![(3, 1)],
        vec![(1, 2), (3, 5)],
        vec![],
        vec![(0, 3)],
    ];
    for (shop, d) in dijkstra(&adj, 0).iter().enumerate() {
        if *d == u64::MAX {
            println!("shop {shop}: unreachable");
        } else {
            println!("shop {shop}: {d} min");
        }
    }
}

shop 0: 0 min
shop 1: 3 min
shop 2: 1 min
shop 3: 4 min
shop 4: unreachable

Shop 1 is 4 minutes away directly, but 3 minutes via shop 2: Dijkstra settles shop 2 first (distance 1), improves shop 1 to 3, and later skips the stale (4, 1) entry.

Each edge can push one heap entry, and each push or pop costs O(log V), so the whole thing is O((V + E) log V). Navigation apps, network routing protocols (OSPF) and game pathfinding (A*, which adds a distance estimate) all build on it.

Common mistakes

  • Negative weights. A settled distance could still be beaten later; Dijkstra gives wrong answers. (Bellman-Ford handles negative weights, more slowly.)
  • A max-heap. Without Reverse, the heap hands you the farthest node first.
  • No stale check. Without if d > dist[u] { continue; }, outdated entries re-relax edges with wrong distances (wasted work, and wrong answers in variants).
  • Overflow. u64::MAX + weight panics in a debug build. Only add weights to distances you've actually reached (popped nodes always have one).
  • Putting the node first in the tuple. The heap orders tuples by their first field, so it must be the distance.
