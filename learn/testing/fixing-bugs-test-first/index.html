Fixing bugs test-first

Tests aren't only for after the code is written. Many developers write them first.

Test-driven development

TDD is a short loop, repeated many times:

  1. Red: write a test for the next small piece of behavior. Run it and watch it fail (that proves the test can fail).
  2. Green: write the simplest code that makes it pass.
  3. Refactor: clean up the code, rerunning the tests to make sure nothing broke.

Bugs: reproduce, then fix

Even teams that don't do strict TDD follow it for bugs. When a bug is reported, first write a test that reproduces it. It fails. Then fix the code until it passes. That test, a regression test, stays in the suite forever, so the bug can't quietly come back.

A bug report says "two spaces between words count as an extra word":

fn word_count(text: &str) -> usize {
    text.split(' ').count()
}

fn main() {
    println!("{}", word_count("hello world"));
    println!("{}", word_count("hello  world"));
    println!("{}", word_count(""));
}

Splitting on single spaces creates empty "words" between two spaces (and one empty word for an empty string). The regression tests come first:

#[test]
fn double_spaces_do_not_add_words() {
    assert_eq!(word_count("hello  world"), 2);
}

#[test]
fn empty_text_has_no_words() {
    assert_eq!(word_count(""), 0);
}

Both fail. The fix is to split on runs of whitespace, and now everything passes:

fn word_count(text: &str) -> usize {
    text.split_whitespace().count()
}

fn main() {
    assert_eq!(word_count("hello world"), 2);
    assert_eq!(word_count("hello  world"), 2);
    assert_eq!(word_count(""), 0);
    assert_eq!(word_count("  tabs\tand\nnewlines "), 3);
    println!("all fixed");
}

Reading a failing test

When cargo test reports a failure, read it top to bottom: which test failed, the panic message (for assert_eq!, the left and right values), and the file and line. A test can fail because the code is wrong or because the test is wrong; check the expected value against the specification before "fixing" the code.

Common mistakes

  • Fixing first, testing later (or never). Without a test that failed before the fix, you don't know the fix fixed anything.
  • Deleting or loosening a failing test to make the suite green. The test is usually telling you something true.
  • Fixing only the reported input. Ask what the bug's whole family looks like (two spaces, three spaces, tabs, leading spaces) and test a few.
