Library errors with thiserror

In the custom errors module you built error enums by hand: the enum, an impl Display with a match giving each variant a message, and an empty impl std::error::Error. That design is exactly right. It's also a lot of typing, and the boilerplate grows with every variant. thiserror is a derive macro that writes those impls for you:

use thiserror::Error;

#[derive(Debug, Error)]
enum WithdrawError {
    #[error("amount must be positive")]
    ZeroAmount,
    #[error("insufficient funds: need {needed}, have {available}")]
    InsufficientFunds { needed: u64, available: u64 },
    #[error("account {0} is frozen")]
    Frozen(String),
}

fn withdraw(balance: u64, amount: u64) -> Result<u64, WithdrawError> {
    if amount == 0 {
        return Err(WithdrawError::ZeroAmount);
    }
    if amount > balance {
        return Err(WithdrawError::InsufficientFunds { needed: amount, available: balance });
    }
    Ok(balance - amount)
}

fn main() {
    println!("{:?}", withdraw(100, 30));
    for amount in [0, 500] {
        match withdraw(100, amount) {
            Ok(left) => println!("left: {left}"),
            Err(e) => println!("error: {e}"),
        }
    }
    println!("{}", WithdrawError::Frozen(String::from("ACC-7")));
}

Ok(70)
error: amount must be positive
error: insufficient funds: need 500, have 100
account ACC-7 is frozen

Piece by piece:

  • #[derive(Debug, Error)]: Error (from thiserror) generates impl std::error::Error and impl Display. The Error trait requires Debug too, so derive both.
  • Each #[error("...")] is that variant's Display message. Inside it, {0} is the first tuple field and {needed} a named field. Format specs work as in format!: {0:?} uses Debug (quotes around strings), {amount:.2} rounds.
  • The result is the same code you'd write by hand: no runtime cost, and thiserror doesn't appear in your public API (callers just see an enum implementing Error), so you could remove it later without breaking anyone.
  • Callers can match on the variants and react differently to each one. That's the point of a typed error, and why libraries use them.

A struct works too, for an operation that can fail in only one way:

use thiserror::Error;

#[derive(Debug, Error)]
#[error("invalid color {input:?}: expected #rrggbb")]
struct ParseColorError {
    input: String,
}

fn main() {
    let e = ParseColorError { input: String::from("teal") };
    println!("{e}");
}

invalid color "teal": expected #rrggbb

Writing good messages

The Rust API guidelines say error messages are lowercase, without a trailing period, and short. The reason: messages get chained into sentences like loading config: line 3: invalid number, and capitals and periods in the middle look wrong. Say what went wrong and include the values that help (the amount, the account, the input).

Common mistakes

Every variant needs a message. Forget one and thiserror tells you at compile time:

use thiserror::Error;

#[derive(Debug, Error)]
enum LoadError {
    #[error("file is empty")]
    Empty,
    TooBig(usize),
}

fn main() {
    println!("{}", LoadError::Empty);
}

error: missing #[error("...")] display attribute
  • Forgetting Debug in the derive gives error[E0277]: `LoadError` doesn't implement `Debug` : std::error::Error requires it.
  • Naming a field that doesn't exist in the message, like {amount} when the field is needed, is a compile error too. Typos can't sneak into production messages.
